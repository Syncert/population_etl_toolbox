# Beta schema steps

Apply these checked-in SQL files in **manifest order**, which is the order `sql/bootstrap/warehouse_manifest.json` declares and `scripts/apply_warehouse_manifest.py` applies. It is not numeric order, and numeric order does not work: `004` alters a relation `src/data_ingestion_toolbox/fred/DDL/silver_fred.sql` creates, `024` alters one created by `gold_acs.sql`, `021` and `023` run directly after `002`, `013` runs before the reference phase, `015` runs in the silver phase, and `003` runs second to last. The list below is numbered for reading; the manifest decides when each step runs, and each entry names the phase it runs in. During the beta prototype, rebuilding the database and re-ingesting source history is the default rollback/cutover strategy; production-style compatibility migrations are not required.

The schema these steps produce is checked in at
`tests/sql/warehouse_schema_snapshot.txt` and compared on every push
(DB-051). After a deliberate DDL change, regenerate it and review the diff as
part of the change:

```bash
RUN_INTEGRATION_TESTS=1 TEST_POSTGRES_HOST=127.0.0.1 TEST_POSTGRES_PORT=55432   TEST_POSTGRES_USER=population_test TEST_POSTGRES_PASSWORD=population_test   TEST_POSTGRES_DATABASE=population_etl_test   python -m tests.support.schema_snapshot --write
```

An unmirrored change is a red job rather than a surprise on a shared
warehouse, and that is the point: a step here and a phase file later in the
manifest can define the same view, and before the snapshot whichever ran last
simply won.

Files must remain safe to rerun during bootstrap and must carry the constraints needed by the active design. Do not edit a step after other shared environments depend on it; add the next sequence instead.

A step here carries only what a rerunnable phase file cannot: a data rewrite,
or a constraint swap on a populated table. A relation's *definition* belongs to
the source that owns it, under `src/data_ingestion_toolbox/<source>/DDL/` and
`<source>/gold_<subject>/DDL/`, where the manifest applies it and the source's
`ensure_*_schema` task re-applies it on every DAG run. A view body restated in
a migration is a second copy that drifts, and the entries below record what
happened when three of them accumulated: `gold_cdc.metric_publisher` had three
definitions in three files, and whichever the manifest ran last simply won.

Several steps are marked **superseded and no longer applied**. The manifest
does not name them and no bootstrap runs them; the file stays on disk as a
pointer at the relations' new home, because a number recorded in a runbook or
a `control` row has to lead somewhere. Nothing is lost by them not running: a
warehouse that already applied them is unchanged, and a fresh one gets the
same objects from the phase files.

A warehouse built before a step was retired keeps its ledger row for it in
`control.schema_migration_state`. That is harmless and needs no cleanup:
`warehouse_manifest.compare_recorded` walks the manifest and asks what the
ledger holds for each asset, so a row the manifest no longer names is never
read. Deleting those rows would erase the only record that the step ran here.

Current sequence:

1. `001_raw_capture_control_foundation.sql` creates immutable response capture and control-plane request/run state. Manifest phase: `foundation`.
2. `002_gold_glossary_decoupling.sql` creates the provider-neutral publisher registry, harvest state, metric source-fact columns, and durable publisher-ready outbox. Manifest phase: `glossary-migration`.
3. `003_semantic_policy_extraction.sql` removes authored policy from the shared metric contract after source report and API consumers have been cut over. It is part of every fresh bootstrap. Manifest phase: `semantic-cutover`.
4. `004_fred_capture_cutover.sql` creates `silver_fred.observation_revision`, so FRED revisions are parsed in silver from an immutable capture rather than at fetch time (ARCH-007). Manifest phase: `source-cutover`.
5. `005_census_acs_capture_cutover.sql` does the same for Census ACS: `silver_census.observation_revision` keeps every cell of a captured response array with its row, column, and header (ARCH-005). Manifest phase: `source-cutover`.
6. `006_bls_capture_cutover.sql` does the same for BLS: `silver_bls.observation_revision` keys each observation to its capture, program, and series (ARCH-006). Manifest phase: `source-cutover`.
7. `007_remove_legacy_parsed_raw.sql` removes the beta-era parsed-observation staging relations after the capture-first cutover. Manifest phase: `source-cutover`.
8. `008_geography_reference_cutover.sql` removes ACS geography ownership after the versioned shared-reference schema is installed. Manifest phase: `geography-cutover`.
9. `009_census_pep_registry.sql` adds the Census PEP registry and control state. Manifest phase: `source-registry`.
10. `010_cdc_pipeline.sql` **is superseded and no longer applied.** It added the CDC capture, silver, and gold contract; those relations now live under `src/data_ingestion_toolbox/cdc/`, where the manifest applies them and `cdc_ingest`'s `ensure_cdc_schema` task re-applies them every run. The file is kept as a pointer at its new home, so the number a runbook or a `control` row records still leads somewhere.
11. `011_fbi_ucr_pipeline.sql` **is superseded and no longer applied.** It added `control.fbi_ucr_release`, the `silver_fbi` release/agency/observation model, and the `gold_fbi` publication views; they now live under `src/data_ingestion_toolbox/fbi_ucr/` and are re-applied by `fbi_ucr_ingest`'s `ensure_fbi_schema` task.
12. `012_usda_nass_crop_pipeline.sql` **is superseded and no longer applied.** It added the USDA NASS Quick Stats capture, silver, and gold crop-data contract; those relations now live under `src/data_ingestion_toolbox/usda_nass/` and are re-applied by `usda_nass_crop_ingest`'s `ensure_nass_schema` task.
13. `013_data_quality_evidence.sql` adds the append-only warehouse data-quality run and result evidence tables. Manifest phase: `quality-foundation`.
14. `014_release_publisher_measure_identity.sql` **is superseded and no longer applied.** It replaced the CDC, FBI, and USDA NASS publisher and measure-export views so each exposes one row per measure identity instead of one row per published release -- grouping by the release watermark made the glossary harvest fail, and the USDA NASS measures endpoint duplicate every measure, as soon as a second release was published. That shape is now what the sources' own `publisher.sql` and `gold_nass.sql` define, in the one place each view is defined.
15. `015_census_pep_historical_series.sql` widens the Census PEP contracts from the 2020s decade to every decade the Bureau publishes. The registry assumed one series that began at the 2020 estimates base, shipped as a plain CSV, and dated every observation to July; this relaxes those constraints, adds the columns that distinguish one decade's publication from another (`series_kind`, `era`, `native_grain`, `derivation`, `archive_member`), and registers the closed decades. It changes no value already served. Manifest phase: `silver`.
16. `016_publisher_harvest_fingerprint.sql` adds `gold_glossary.publisher_harvest_state.last_content_fingerprint` and `last_harvest_forced`. The harvest skipped whenever a publisher's `publication_time` had not advanced, and that time comes from the facts a publisher reads — so a change to what the publisher *says* (an identity, display name, units, grains, lineage, or the set of keys it emits) moved nothing the guard could see, and the catalog kept serving identities the warehouse no longer published. A NULL fingerprint means never recorded, so every existing row re-harvests once after this step. Manifest phase: `glossary`.
17. `017_serving_full_reserve_run.sql` adds `control.serving_refresh_state.last_full_reserve_started_at`. A forced full re-serve rewrites every calendar year regardless of its watermark, which leaves the driver unable to tell a year that is already done from one that only looks done; recording when the run began makes a chunk completing at or after that instant done *for this run*, so an Airflow retry resumes at the year it stopped on instead of re-running hours of completed chunks. Manifest phase: `glossary`.
18. `018_geo_grain_vocabulary.sql` defines `gold_glossary.geo_grain(text)`, the one geography-grain vocabulary the catalog publishes and the serving routes filter on (`NATIONAL`, `STATE`, `COUNTY`, `PLACE`, `AGENCY`). It also replaced the CDC and USDA NASS publisher views to derive their grains through it -- they published `NATION` from `geo_type`, and NASS filtered on `agg_level_desc`, whose word is `NATIONAL`, so every national NASS statistic in the catalog was unanswerable through its own filter. Those two view bodies are no longer restated here; the sources' own `publisher.sql` files define them and call the same function. Manifest phase: `glossary`.
19. `019_stratum_shape_contract.sql` constrains `silver_cdc.dim_stratum.strata` and `silver_cdc.observation_revision.strata` to JSON arrays. `/api/v1/cdc/observations` publishes a stratum with every value and declares it a list; the CDC parser produces one, but `jsonb` accepts an object, a string, a number, or `null` just as happily, and nothing between the insert and the response model checked. A stratum stored as an object was accepted by every write path and then answered `500 The API failed to complete this request` on every page that included the row. Manifest phase: `source-fix`.
20. `020_resolved_geography_serving.sql` **is superseded and no longer applied.** It served only rows whose geography resolved from `gold_cdc.health_observation` and `gold_nass.crop_observation`, and aggregated the CDC and USDA NASS publishers' `valid_geo_grains` from the same rows: their two siblings filtered on the release status alone, so `/observations` paged out rows with `geo_id: null` and a `geo_level` outside the served vocabulary, and a NASS product with one AGRICULTURAL DISTRICT row advertised `UNSUPPORTED` as a grain a client could ask for. The rows stay in silver with the resolution ledger, and `unmapped` stays served, because its grain is in the vocabulary and DB-003's rule is that such a miss is explicit rather than dropped. Those predicates are part of the sources' own gold and publisher DDL now.
21. `021_geo_grain_vocabulary_early.sql` defines `gold_glossary.geo_grain(text)` beside the schema it lives in, before the `gold` and `publisher` phases whose views now call it. 018 created the same function in the `glossary` phase, which runs after those views are created, so a publisher DDL calling it would have failed at `CREATE VIEW` time on a fresh bootstrap; 018 is left as it shipped and its `CREATE OR REPLACE` of the same body is a no-op. The vocabulary is unchanged. Manifest phase: `glossary-migration`.
22. `022_fbi_publisher_geo_grain.sql` **is superseded and no longer applied.** It replaced `gold_fbi.metric_publisher` so its `valid_geo_grains` go through `gold_glossary.geo_grain` like every other publisher's, and it had to be a new step for a reason it recorded itself: FBI's was "the one publisher whose last definition sits in a migration rather than a phase file, and that step is not edited in place". It sits in a phase file now -- `src/data_ingestion_toolbox/fbi_ucr/gold_fbi/DDL/publisher.sql` -- which is what this step was working around.
23. `023_geo_name_vocabulary_early.sql` defines `gold_glossary.geo_name(place_name, county_name, state_name, geo_id)`, the one published name of a geography. `gold_glossary.dim_geography` coalesced place first and all six observation contract views coalesced county first, so a place answered under its own name on `/catalog/geographies` and under its state's name on every observation route -- one geography, two names, each expression locally correct. Installed in the `glossary-migration` phase for the reason 021 is: a view's body resolves at `CREATE VIEW`, so a function the contract views call must already exist.
24. `024_served_place_name.sql` adds `place_name` to the three reporting tables and the three latest-value tables, so those views can call `geo_name` with the same arguments the catalog does instead of approximating it, and backfills the column from the geography catalog for rows already served. `ALTER TABLE` can only append, while the table DDL declares the column beside `county_name` for a fresh bootstrap; what has to hold is that `rpt_*` and `mv_*` agree with *each other*, because the latest-value refreshes insert `d.*` positionally, and both are altered in this one step. Manifest phase: `glossary`.
25. `025_county_label_is_not_reviewed.sql` publishes a county resolved from the FBI's county *label* as `confidence_class = 'derived'` and `resolution_method = 'county_label_match'`, and rewrites the rows the old code wrote. The join upper-cases the label, strips one legal suffix, and requires a unique match against `silver_ref.dim_geo_current.county_name` -- exact and uniqueness-checked, and still a name. It claimed `reviewed_county_name_crosswalk` / `reviewed`, the token the place path earns from a table with a reviewer, an evidence URL and a review note, so `gold_fbi.agency_observation_area_filter` published `reviewed` over a name match and a consumer filtering on it could not tell the two apart. Its two constraint swaps now follow the rewrite rather than precede it: `ADD CONSTRAINT` validates every existing row immediately, so the order it shipped in could only run against an empty table -- a fresh bootstrap -- and failed on every warehouse actually holding the rows it corrects (DB-057). Also adds `agency_county_unresolved` to the two `geography_status` vocabularies: a provider-labelled county that did not resolve read as `agency_only`, which says the provider named no county at all -- one is this pipeline's gap and the other a fact about the source, and only the first is something an operator can act on. Manifest phase: `source-fix`.

26. `026_released_date_is_not_the_refresh_clock.sql` corrects the `as_of_date` values the refresh clock already materialised into the BLS, FRED and ACS reporting and latest-value tables, setting each to its own `updated_at::DATE` -- which in these relations *is* the silver row's `ingested_at`, so the correction is exact and needs no re-serve. The three fact views published `CURRENT_DATE AS as_of_date`, so a served release was the calendar day a chunk was last written: the driver re-serves only changed years, so re-serving two years on two days listed two published releases the provider never published, and a full re-serve collapsed every release into one. The view definitions are not restated here -- they live in the phase DDL files the bootstrap applies before this step and the DAGs re-apply every run, and a second copy of a sixty-line view body is a copy that drifts. Manifest phase: `glossary`.

27. `027_acs_bls_fact_lineage.sql` gives `silver_census.fact_demographics` and `silver_bls.fact_labor_statistics` the `capture_id`, `source_value` and `value_status` that five of the seven silver facts already carried, and rewrites the rows written before them: a fact with no estimate is `absent` (ACS) or `missing` (BLS) rather than the column default's `valid`. Their revision relations have distinguished absent/blank/sentinel/invalid and valid/missing/invalid all along; the fact aggregation kept only the number, so a cell Census suppressed or an observation BLS footnoted reached serving as no row at all, and a consumer could not tell it from one the provider never published. It also adds to `silver_fred.fact_economic_indicators` the check its revision has always had -- `value_status` there defaults to `valid` and nothing tied it to the number, so a writer that set no status claimed a published value it did not have. The column definitions live in the phase files; this step is what a populated warehouse needs. Manifest phase: `source-fix`.

28. `028_serving_publishes_a_withheld_value.sql` lets the ACS and BLS serving relations hold a value the provider withheld: it relaxes their `NOT NULL` value columns and adds `value_status`, `source_value` and `capture_id` to the reporting and latest-value tables. 027 gave the silver facts those columns; serving still dropped the rows, because the fact views filtered on a non-null value and the reporting tables had nowhere to put one. Measured on the internal stack, that was 31,481,530 of 99,783,997 ACS fact rows -- every cell Census suppressed, indistinguishable to a consumer from a geography that does not exist. The constraint validates without a rewrite: every row already served carries a value, which was the filter's whole effect, and the withheld rows arrive with the re-serve that follows. Manifest phase: `publisher`.

29. `029_nass_combined_counties_are_not_counties.sql` rewrites the USDA NASS rows published under county code `998` to the unsupported geography the silver code now gives them. Quick Stats uses `998` for "OTHER (COMBINED) COUNTIES" -- the counties it suppresses for disclosure, combined once per agricultural district -- so every district of a state collided on one fabricated `state:SS|county:998` identity, which was `unmapped` and therefore still served at the COUNTY grain. The rows stay in silver with their district evidence (`geo_source_code = SS998`, `asd_code`); gold and the publisher exclude them. Silver writes are `ON CONFLICT DO NOTHING`, so replay cannot correct a stored row, which is why this is a step. No value changes and nothing is deleted except the county-typed resolution ledger rows whose identity no longer exists. It also re-queues the USDA NASS publisher-ready event: the rewrite changes the publisher's `valid_geo_grains` without moving a publication time, and the scheduled harvest only visits a publisher with a pending event, so without it the catalog kept advertising a county map for seven measures with no county data. Manifest phase: `source-fix`.

One entry per file, numbered as the file is: a step whose ordinal and filename disagree is a step a reader cannot find. `015`–`017` went undocumented here for three releases while running in every bootstrap, which is why `tests/unit/shared/test_warehouse_manifest.py` now fails when the manifest applies a migration this list does not describe.
